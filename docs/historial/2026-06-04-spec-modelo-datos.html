Spec — Modelo de Datos: Estudio Nancy Sol

Versión 1.0 · 2026-06-04 · Docs/specs/2026-06-04-modelo-datos-estudio-nancysol.html

1. Decisiones cerradas

D1 — Atribución cobro → ganancia para retiros CERRADA

Opción A (proporcional): la ganancia cobrada se calcula como ratio del total cobrado sobre el total presupuestado, aplicada a la ganancia total de la obra.

ganancia_cobrada = (total_cobrado_obra / total_presupuesto_obra) × ganancia_total_obra

No requiere linkear cobros a ítems individuales. Converge naturalmente cuando se cobra la obra completa.

D2 — Rubro en presupuesto_items CERRADA

Opción A (FK estricta nullable): rubro_id FK a rubros, nullable. Si no hay proveedor o no matchea, se elige de la lista. Texto libre no disponible; los ~30 rubros reales del catálogo cubren todos los casos reales.

Valores por defecto en UI: al crear un ítem, valor_presupuesto se calcula como valor_proveedor × 1.21 (o × TC si son USD). valor_final default = valor_presupuesto. Ambos son editables.

Trigger + CHECK anti-silencio USD: el TC de un ítem USD debe quedar lockeado al momento de cargarlo. El trigger BEFORE completa el TC desde el fallback de la obra si falta. El CHECK es la red final (dispara solo si fallback también es null).

-- Trigger que completa el TC desde el fallback de la obra
create or replace function public.tf_set_tc_from_fallback()
returns trigger as $$
begin
  if NEW.moneda = 'USD' and NEW.tc_item is null then
    SELECT tipo_cambio_fallback INTO NEW.tc_item
    FROM obras WHERE id = NEW.obra_id;
  end if;
  if NEW.moneda_proveedor = 'USD' and NEW.tc_proveedor is null then
    SELECT tipo_cambio_fallback INTO NEW.tc_proveedor
    FROM obras WHERE id = NEW.obra_id;
  end if;
  return NEW;
end;
$$ language plpgsql;

create trigger tr_set_tc_item
  before insert or update on public.presupuesto_items
  for each row execute function public.tf_set_tc_from_fallback();

-- CHECK como red final (solo dispara si fallback también es null)
alter table public.presupuesto_items add constraint chk_tc_item
  check (moneda = 'ARS' or tc_item is not null);
alter table public.presupuesto_items add constraint chk_tc_proveedor
  check (moneda_proveedor = 'ARS' or tc_proveedor is not null);
-- movimientos_caja.tipo_cambio es NOT NULL, no requiere check.

3. Views (las "fórmulas" del Excel, recalculadas solas)

3.1 v_presupuesto_items — Ítems con columnas derivadas

SELECT pi.*, obra.honorario_override, obra.tipo_cambio_fallback, -- TC efectivo: currency-aware. ARS → 1. USD → TC de la transacción, -- o fallback de la obra si null (permite cargar muchos USD sin repetir TC). CASE WHEN pi.moneda = 'ARS' THEN 1 ELSE COALESCE(NULLIF(pi.tc_item, 0), obra.tipo_cambio_fallback) END AS tc_item_efectivo, CASE WHEN pi.moneda_proveedor = 'ARS' THEN 1 ELSE COALESCE(NULLIF(pi.tc_proveedor, 0), obra.tipo_cambio_fallback) END AS tc_proveedor_efectivo, -- Montos en ARS (convertidos con TC efectivo, reutilizados entre columnas) (pi.valor_proveedor * CASE WHEN pi.moneda_proveedor = 'ARS' THEN 1 ELSE NULLIF(pi.tc_proveedor, 0) END) AS valor_proveedor_ars, (pi.valor_presupuesto * CASE WHEN pi.moneda = 'ARS' THEN 1 ELSE NULLIF(pi.tc_item, 0) END) AS valor_presupuesto_ars, (pi.valor_final * CASE WHEN pi.moneda = 'ARS' THEN 1 ELSE NULLIF(pi.tc_item, 0) END) AS valor_final_ars, -- Honorario en ARS (pi.valor_final * CASE WHEN pi.moneda = 'ARS' THEN 1 ELSE NULLIF(pi.tc_item, 0) END * COALESCE(obra.honorario_override, sett.honorario_default)) AS honorario_ars, -- Total en ARS (incluye honorario) (pi.valor_final * CASE WHEN pi.moneda = 'ARS' THEN 1 ELSE NULLIF(pi.tc_item, 0) END * (1 + COALESCE(obra.honorario_override, sett.honorario_default))) AS total_ars, -- Adicional [INTERNO]: presupuesto - costo, en ARS. Reutiliza columnas ya convertidas. (valor_presupuesto_ars - valor_proveedor_ars) AS adicional_ars, -- Ganancia [INTERNO]: total - costo, en ARS. Incluye honorario. -- (total_ars ya incluye honorario = K en el Excel) (total_ars - valor_proveedor_ars) AS ganancia_ars FROM presupuesto_items pi JOIN obras obra ON obra.id = pi.obra_id CROSS JOIN settings sett

TC currency-aware: si moneda='ARS' se fuerza TC=1 siempre, sin importar el fallback de la obra. Si moneda='USD' y tc_item es null, se usa el fallback de la obra; si el fallback tampoco existe, la UI debe pedir el TC (no se puede convertir sin TC).

3.2 v_obra_totales — Totales por obra

SELECT obra_id, COUNT(*) AS total_items, -- Todos los montos en ARS (las columnas _ars ya están convertidas) SUM(valor_proveedor_ars) AS total_costo_ars, SUM(valor_presupuesto_ars) AS total_presupuesto_ars, SUM(valor_final_ars) AS total_final_ars, SUM(ganancia_ars) AS total_ganancia_ars, SUM(honorario_ars) AS total_honorarios_ars, SUM(adicional_ars) AS total_adicional_ars, SUM(total_ars) AS total_general_ars, -- Total USD puro (ítems en USD, sin conversión) SUM(CASE WHEN pi.moneda = 'USD' THEN pi.valor_final ELSE 0 END) AS total_final_usd, SUM(CASE WHEN pi.moneda = 'USD' THEN pi.valor_proveedor ELSE 0 END) AS total_costo_usd FROM v_presupuesto_items pi GROUP BY obra_id

3.3 v_caja_saldo — Running balance por obra (cobros + pagos + retiros)

-- UNION: movimientos de caja y retiros tienen esquemas distintos. -- La tabla movimientos_caja cubre cobros y pagos. -- La tabla retiros es separada y tiene monto_nancy/monto_sol. -- El running balance es la suma de los tres flujos en ARS. WITH caja_union AS ( -- Cobros: monto positivo SELECT obra_id, id, fecha, 'cobro_cliente' AS tipo, mc.monto * mc.tipo_cambio AS monto_ars FROM movimientos_caja mc WHERE mc.tipo = 'cobro_cliente' UNION ALL -- Pagos: monto negativo SELECT obra_id, id, fecha, 'pago_proveedor' AS tipo, -mc.monto * mc.tipo_cambio AS monto_ars FROM movimientos_caja mc WHERE mc.tipo = 'pago_proveedor' UNION ALL -- Retiros: suma de ambos montos (Nancy + Sol), negativos SELECT r.obra_id, r.id, r.fecha, 'retiro' AS tipo, -(r.monto_nancy + r.monto_sol) * r.tipo_cambio AS monto_ars FROM retiros r ) SELECT obra_id, id, tipo, monto_ars, SUM(monto_ars) OVER ( PARTITION BY obra_id ORDER BY fecha, created_at ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW ) AS saldo_acumulado_ars FROM caja_union ORDER BY obra_id, fecha

Importante: fecha se usa para ordenar; created_at desempata dentro del mismo día. El saldo acumulado en ARS es lo que reemplaza la columna "Saldo en Caja" del Excel. No es el saldo disponible para retiros (ese viene de v_ganancia_cobrada vía v_retiros_convergencia).

3.4 v_pagos_por_proveedor — Agregación por proveedor (reemplaza el pivot de 86 columnas)

SELECT obra_id, proveedor_id, p.nombre AS nombre_proveedor, SUM(mc.monto * mc.tipo_cambio) AS total_pagado_ars FROM movimientos_caja mc JOIN proveedores p ON p.id = mc.proveedor_id WHERE mc.tipo = 'pago_proveedor' GROUP BY obra_id, proveedor_id, p.nombre ORDER BY obra_id, total_pagado_ars DESC

3.5 v_saldos_obra — Los labels del Excel

SELECT obra_id, -- Saldo a cobrar del cliente (total presupuesto - cobros recibidos) (SELECT SUM(total_general_ars) FROM v_obra_totales WHERE obra_id = o.id) - (SELECT SUM(monto_ars) FROM v_caja_saldo WHERE obra_id = o.id AND tipo = 'cobro_cliente') AS saldo_a_cobrar_ars, -- Deuda a proveedores (suma de todos los pagos a proveedores) (SELECT SUM(monto_ars) FROM v_caja_saldo WHERE obra_id = o.id AND tipo = 'pago_proveedor') AS deuda_proveedores_ars, -- Pagado al cliente (total cobros) (SELECT SUM(monto_ars) FROM v_caja_saldo WHERE obra_id = o.id AND tipo = 'cobro_cliente') AS total_cobrado_ars, -- Saldo en caja (cobros - pagos - retiros) (SELECT saldo_acumulado_ars FROM v_caja_saldo WHERE obra_id = o.id ORDER BY fecha DESC LIMIT 1) AS saldo_caja_ars FROM obras o

3.6 v_ganancia_cobrada — Ganancia atribuible a cobros efectivos (base caja) USA D1

-- D1: ganancia cobrada = (total_cobrado / total_facturado) × ganancia_total -- Denominador = total_general_ars (suma de K = total, no de H = presupuesto). -- total_cobrado_ars viene de movimientos_caja, no de v_obra_totales. SELECT obra_id, (SELECT SUM(monto_ars) FROM v_caja_saldo WHERE obra_id = ot.obra_id AND tipo = 'cobro_cliente') AS total_cobrado_ars, ot.total_general_ars AS total_facturado_ars, -- denominador: suma de K (total), no de H ot.total_ganancia_ars, CASE WHEN ot.total_general_ars > 0 THEN ( (SELECT SUM(monto_ars) FROM v_caja_saldo WHERE obra_id = ot.obra_id AND tipo = 'cobro_cliente') / ot.total_general_ars ) * ot.total_ganancia_ars ELSE 0 END AS ganancia_cobrada_ars FROM v_obra_totales ot

Denominador = total_facturado_ars (K = total): el ratio usa la suma de los totales facturados (honorario incluido), no los presupuestos brutos. Así cuando se cobra el 100% de la obra, ganancia_cobrada converge exactamente a total_ganancia_ars. Si el cliente paga solo $600k de $1M facturado (con $150k de honorario), cobra proporcionalmente $90k de ganancia.

3.7 v_retiros_convergencia — Convergencia 50/50 y disponible para retirar

SELECT r.obra_id, -- Retiros acumulados por socia (ya en ARS) SUM(r.monto_nancy * r.tipo_cambio) AS total_retiros_nancy_ars, SUM(r.monto_sol * r.tipo_cambio) AS total_retiros_sol_ars, SUM((r.monto_nancy + r.monto_sol) * r.tipo_cambio) AS total_retiros_ars, -- Target: 50/50 de la ganancia cobrada gc.ganancia_cobrada_ars, (gc.ganancia_cobrada_ars * COALESCE(o.split_nancy_override, s.target_reparto_nancy)) AS target_nancy_ars, (gc.ganancia_cobrada_ars * COALESCE(o.split_sol_override, s.target_reparto_sol)) AS target_sol_ars, -- Diferencia vs target (positivo = a favor, negativo = excedente) (SUM(r.monto_nancy * r.tipo_cambio) - (gc.ganancia_cobrada_ars * COALESCE(o.split_nancy_override, s.target_reparto_nancy))) AS diferencia_nancy_ars, (SUM(r.monto_sol * r.tipo_cambio) - (gc.ganancia_cobrada_ars * COALESCE(o.split_sol_override, s.target_reparto_sol))) AS diferencia_sol_ars, -- Disponible para retirar (ganancia cobrada - retiros hechos) (gc.ganancia_cobrada_ars - SUM((r.monto_nancy + r.monto_sol) * r.tipo_cambio)) AS disponible_para_retirar_ars FROM retiros r JOIN obras o ON o.id = r.obra_id JOIN settings s ON true JOIN v_ganancia_cobrada gc ON gc.obra_id = r.obra_id GROUP BY r.obra_id, o.split_nancy_override, o.split_sol_override, s.target_reparto_nancy, s.target_reparto_sol, gc.ganancia_cobrada_ars

Warning, no bloqueo: si disponible_para_retirar_ars es negativo, se muestra un warning en la UI pero se permite registrar el retiro igual. La regla de negocio no bloquea; solo informa.

4. Bimoneda — Conversiones y reglas

4.1 Almacenamiento

Todo monto se guarda en su moneda nativa (ARS o USD) + el TC correspondiente a esa transacción:

  • presupuesto_items.valor_proveedor + tc_proveedor
  • presupuesto_items.valor_presupuesto + tc_item
  • presupuesto_items.valor_final + tc_item
  • movimientos_caja.monto + tipo_cambio
  • retiros.monto_nancy/sol + tipo_cambio

4.2 Conversión a ARS

Para consolidar en ARS, siempre se usa el TC de la transacción, nunca un TC genérico:

monto_ars = monto_nativo × tipo_cambio_de_esa_transaccion

Si tc_* es null, se usa obras.tipo_cambio_fallback. Si el fallback tampoco está definido, es un error (la UI debe pedir que se ingrese el TC).

4.3 Fallback por obra y lock-in de TC

Cada obra puede tener un tipo_cambio_fallback (ej. 1200 ARS/USD). El trigger tf_set_tc_from_fallback lo copia al ítem en el momento de la inserción si el TC está nulo. Una vez grabado, el TC queda lockeado en el ítem (no cambia si después se modifica el fallback de la obra). Esto es correcto: el TC debe ser el de la fecha del ítem, no un valor futuro.

Flujo completo:

  • USD + tc_item null + fallback existe → trigger completa tc_item → pasa CHECK → TC lockeado.
  • USD + tc_item null + fallback null → trigger no llena nada → CHECK rechaza (error en BD).
  • ARS → tc forzado a 1, sin consultar fallback nunca.

4.4 Suma cross-moneda

Regla anti-bug: nunca sumar montos en distintas monedas sin convertir primero a ARS con el TC de cada transacción. Las views de agregación (v_obra_totales, v_caja_saldo) siempre convierten antes de sumar.

4.5 Toggle USD

Como se guardan montos nativos en ambas monedas, un toggle USD en la UI es trivial: se muestran los montos tal cual están, sin conversión, usando la columna moneda como filtro.

6. Grants y RLS

Todas las tablas en public incluyen grants explícitos. RLS habilitado en todas.

-- Ejemplo para cada tabla:
alter table public.mi_tabla enable row level security;

-- Policy: las 2 socias comparten 1 login (authenticated = admin compartido)
create policy "admin_total" on public.mi_tabla
  for all to authenticated using (true);

-- Grants Data API (para supabase-js / PostgREST)
grant select on public.mi_tabla to authenticated;
grant select, insert, update, delete on public.mi_tabla to authenticated;
grant select, insert, update, delete on public.mi_tabla to service_role;

Por qué no anon: la app es 100% interna con auth. No hay contenido público. El export se genera tras login, en el servidor o componente print-only server-side.

8. Restricciones no negociables

  • Cero refs por posición: todo FK, fórmulas = views, nunca copiadas a mano.
  • UX para no técnicas: simple, sin jerga, imposible romper un cálculo desde la UI.
  • Reglas de negocio en settings + override por obra. Nada hardcodeado.
  • Auth admin compartido (1 login para las 2 socias). Sin rol cliente.
  • Multi-obra desde día 1.
  • Export F–K: campos [INTERNO] nunca se filtran, ni en metadata.
  • Nunca sumar cross-moneda sin convertir vía TC de la transacción.
  • Stack: Nuxt 4 + Vue 3 Composition API <script setup> JS (no TS) + Tailwind + Supabase + Vercel.
  • SSR-safe (onMounted libs cliente, ClientOnly donde aplique).
  • Comentarios en español. Orden Tailwind del proyecto.
